摘要

將技術手冊交給大型語言模型（Large Language Model, LLM）時，常見做法是上傳全書或先做整本摘要，模型因此能回答書籍裡寫過的問題。然而，當工程師接手新工程項目時卻不知道先問什麼、依哪條規則判斷、數字由誰計算。本報告提出六步驟蒸餾方法，將技術手冊由解釋順序改寫為執行順序，封裝成 Skill（Agent Skill）。六步驟依序為定任務、拆知識單元、分流與濃縮、接成流程、封裝、測試與迭代，每一步都訂有作業程序、判斷規則與完成條件，未建置過 Skill 的工程師可以依序照做；知識單元以五個問題判斷，測試分為數值、邏輯、邊界、缺漏、法規與工程情境六類。方法以《Formwork for Concrete Structures》第 4 版[1]建置「模板大師」Skill 驗證。原書第 3 章約 19 頁的側壓力內容，在 Claude 版主檔中濃縮為五列的側壓力決策表，其餘分流至速查表、方法檔、計算程式與審查表；以程式回歸驗證原書例題與表值 103 項全數通過，另記錄 15 項原書勘誤，其中 12 項已確認、3 項待核。同一內容封裝為 Claude、Gemini、ChatGPT 三個平台版本。案例也顯示，使用地法規的查證必須在流程結構化階段插入，延後補做會使全部參考檔重寫。Skill 的計算結果屬工程輔助成果，本報告依風險將應用分為三級，設計與安全決策須經人工專業審查。

關鍵詞　Skill、書籍蒸餾、技術手冊、模板設計、大型語言模型

第一章

一、緒論

1.1 研究背景與動機

技術手冊依知識的邏輯編排，Skill 則要依任務的執行順序運作，兩者之間需要一道轉換。以模板設計為例，原書[1]先說明影響側壓力的因素，再介紹公式、係數表與例題，讀者讀完一章後，自己判斷何時套用哪一式。工程師把這樣的書籍直接交給 LLM，模型讀得到公式，卻缺少三樣東西，分別是接到任務時的提問順序、選用公式的判斷條件，以及可以驗證的計算結果。

1.2 既有做法的限制

上傳全書時，模型每次回答都要從數百頁敘述中檢索，容易取到條件不符的公式，答出的數值也無法追溯出處。先請模型做整本摘要再當成知識檔，摘要會保留章節順序與結論，同時刪掉公式的適用條件與夾限，工程判斷依據的正是這些條件。

兩種做法還共同面對本地化問題。原書依美國規範與英制單位撰寫，國內模板工程須以《營造安全衛生設施標準》（勞動部，115 年 6 月 30 日修正發布）[5]、《結構混凝土施工規範》（內政部，110 年 7 月 13 日修正發布，110 年 9 月 1 日生效）[6]及契約引用的《公共工程施工綱要規範》第 03110 章「場鑄結構混凝土用模板」（行政院公共工程委員會）[7]為首要依據。整本上傳或整本摘要，都無法讓模型知道哪一段該改用國內規定。

1.3 研究目的與範圍

本報告主要目的有二。第一，提出一套六步驟蒸餾方法，讓會使用聊天式 AI、但未建置過 Skill 的工程師，能依循步驟把一本技術手冊轉成可執行的 Skill。第二，以模板大師案例驗證方法，記錄每一步處理前後的內容、檢驗結果與最後產出的 Skill。附錄B 另提供依本方法撰寫的 book-to-skill Skill，讓讀者在對話中由 AI 帶著走完六步驟。適用對象為含有公式、表格、例題與規範依據的工程技術書籍；以敘事為主、缺少可計算內容的書籍不在本報告範圍。

全文架構如圖1。技術知識來源依序經過知識蒸餾、任務建模、Skill 封裝與品質驗證四個階段，對應第三章的六個步驟；依據版本與單位換算的管理貫穿各階段，測試不合格時回到對應階段修正。

第二章

二、書籍與 Skill 的組織差異

2.1 讀者與順序

書籍是寫給想理解主題的人閱讀的，而Skill 則寫給要完成任務的 AI，兩者在組織順序、內容形式與缺資料時的處理方式上存在諸多差異（表1）。

表1　書籍與 Skill 的組織方式比較

比較項目書籍Skill
讀者想理解主題的人要完成任務的 AI
組織順序知識的邏輯順序（章節）任務的執行順序（流程）
主要內容敘述、推導、背景、例題規則、決策表、公式、程式、檢核表

蒸餾的工作主要是改寫順序。能讓 AI 判斷與計算的部分留下，只為幫助理解的部分刪除，留下的內容再依任務重新排列。圖2 以模板設計為例，書籍中的公式推導拆成兩路，適用條件進入判斷步驟，計算式進入計算程式；例題轉為檢核用的驗證項目；背景敘述刪除，或縮成規則旁的一行原因說明。圖2 右欄第 1 步「詢問輸入與依據」在書中找不到對應章節。書只說明公式需要哪些變數，不會寫明接到工作時要先向使用者問什麼；這些詢問項目在步驟四依任務追蹤五問逐步整理，使用地的法規依據則來自步驟一的外部補充清單。

2.2 Skill 的檔案構成

Skill 是一個資料夾，至少包含一個主檔 SKILL.md。主檔開頭以 name 與 description 兩個欄位說明這個 Skill 的名稱與使用時機；需要時才讀取的參考文件放在 references/，可執行的程式放在 scripts/[3,4]。平台以漸進式揭露（Progressive Disclosure）載入 Skill，平時只讀名稱與描述，任務相符時才讀主檔本文，再依主檔中的索引讀取參考檔或執行程式[3]。官方撰寫指引建議主檔本文控制在 500 行以內[4]。

這個載入機制決定了蒸餾成果的放置方式。主檔每次觸發都會被讀取，內容越短越好；查表資料、方法細節與程式放在主檔之外，用到時才讀（圖3）。模板大師的 Claude 版另設 examples/，存放台灣案件的輸入範本與原書例題的輸入輸出。

3.1 步驟一　定任務

Skill 要會做哪些事，必須在閱讀書籍之前決定。沒有任務清單就開始讀，產出會變成全書摘要，Skill 接到工作時仍不知道要做什麼。

作業程序

  1. 列出使用者會交給 Skill 的工作，每件寫成「動詞＋對象＋條件」。10～20 件為參考值，依書的範圍與使用情境增減。
  2. 為每件工作標示類型，分為計算、撰寫、審查、查詢四類。
  3. 逐件寫下工程師做這件事時手邊需要的知識。
  4. 翻閱目錄，把需要的知識對應到章節；對應不到的記入外部補充清單。
  5. 確認使用地依據，包括國家、主管機關與契約規範，並比對它與原書規範體系的差異。
  6. 決定 Skill 的識別名與顯示名稱。

判斷規則

  • 蒸餾範圍取任務需要與書籍中提供的交集。書籍中有、任務用不到的內容，只在術語表或章節摘要留一行。
  • 任務需要、書籍中沒有的內容（例如國內法規），列入外部補充清單，留到步驟四查證，不得憑記憶補寫。
  • 原書規範體系與使用地不同時，在本步驟就定案分工，原書方法作為計算方法，使用地法規作為首要依據。
  • 列到使用者常做的工作類型都已涵蓋、再也列不出新任務時停止，不為湊數拆分同一件工作。

完成條件

  • 任務清單涵蓋使用者常做的計算、撰寫、審查與查詢工作
  • 每件任務都對應到章節或外部補充清單
  • 已記錄使用地依據與原書規範體系的關係

提示範例（通用範本，非本案原檔）

我要把《書名》製作成 Skill。請先不要摘要全書。
請依目錄列出工程師會交給這個 Skill 的 15 件工作，
每件寫成「動詞＋對象＋條件」，標示計算、撰寫、審查或查詢，
並列出所需知識與對應章節。書籍中找不到的知識另列為外部補充清單。

3.2 步驟二　拆知識單元

任務相關章節要拆成可以單獨使用的最小內容，後續的分流與流程才有處理單位。本報告稱這個單位為知識單元，可以是一條規定、一個公式及其適用條件、一張表、一個定義、一個步驟、一個例題或一個失敗教訓。拆解採三遍讀法（表3），判斷一段文字是否成為單元，則用五個問題（圖5），本報告稱為單元五問。第五問專門找出限制、例外、風險與禁止事項，模板工程的支撐失穩、拆模時機與材料缺陷多屬此類，常比公式本身更重要。

表3　三遍讀法

遍次讀什麼做什麼產出
第一遍 掃描目錄、各章標題、公式、表、例題、圖說清點知識資產，標記對應任務清單的章節資產清冊（公式、表、例題、頁碼）
第二遍 精讀任務相關章節，逐段拆成知識單元，每個單元記出處知識單元清單
第三遍 交叉例題、表格、前後章引用例題逐步對公式重算，表格抽格重算，前後章數值比對勘誤候選、驗證項目

作業程序

  1. 第一遍掃描全書，建立資產清冊並記下頁碼。
  2. 第二遍逐段精讀任務相關章節，以單元五問判斷，每個單元給編號並記出處。
  3. 第三遍用例題逐步對公式重算，抽格重算表格，比對前後章數值，記下勘誤候選。
  4. 將單元登錄於知識單元登錄表（附錄表A1）。

判斷規則

  • 五問是主要判斷工具。五問都答不出的段落多屬背景或連接敘述，不列為單元；只答得出第五問的安全原則、定義限制或禁止事項，仍列為單元。
  • 公式連同適用條件、單位與夾限一起拆出，不可只抄式子。
  • 例題記下輸入與答案，供步驟六重算。
  • 說明原因的文字不單獨成為單元，附在相關規則的單元內，供步驟三決定留在主檔或參考檔。

完成條件

  • 任務相關章節全部拆完
  • 例題全部登錄輸入與答案
  • 每個單元都有編號與出處頁碼

提示範例（通用範本，非本案原檔）

請逐段讀第 3 章。每一段先回答五個問題：
能讓讀者做什麼、在什麼條件下適用、需要什麼輸入、結果用在哪裡、
有哪些限制例外風險與禁止事項。
能答的段落列為知識單元，給編號 K3-01 起，記頁碼與式號；
五題都答不出的段落標為背景，不列入。例題另記輸入與答案。

3.4 步驟四　接成流程

分流後的單元仍依類型存放，AI 接到一件工作時，還需要知道先問什麼、先判斷什麼、再算什麼。本步驟從任務清單逐件取出工作，模擬工程師實際的作業順序，依序回答五個問題，把單元串成任務流程，本報告稱為任務追蹤法。

  1. 第一步要先知道什麼，缺了會怎樣。答案成為輸入清單與缺漏時的詢問項目。
  2. 要先判斷什麼。答案決定哪張決策表放在流程前段。
  3. 接著算什麼，用哪個知識單元。答案成為計算順序。
  4. 結果放到哪裡、用什麼格式。答案成為輸出格式與文件章節。
  5. 這一步常犯什麼錯。答案成為該步驟旁的檢查項目。

同一章的其他單元流向主檔以外的檔案（圖8）。Cw 與 Cc 表進入速查表，式(1)～(4)連同式號、適用條件與夾限寫入方法檔 P1，並寫成計算程式的 pressure 子指令；例題成為回歸驗證項目，3 格與公式不符的表值列入勘誤；「表 3-3～3-5 左欄是澆置速率、不是牆高」這項常見誤用寫入主檔的注意事項與章節摘要的反模式。原本約 19 頁的內容，在 Claude 版主檔中只占 F1 的五列決策表。

  2. 模板大師案例中，原書第 3 章約 19 頁濃縮為 Claude 版主檔 F1 的五列決策表，其餘內容分流至速查表、方法檔、計算程式與審查表。計算程式回歸驗證原書例題與表值 103 項全數通過，另記錄 15 項原書勘誤，其中 12 項已確認、3 項待核。程式化計算仍須輸入、單位與適用條件檢核，並以獨立方法交叉驗證。
  3. 本地化查證須在步驟四的每一步插入，並記錄依據的層級與版本。模板大師在 v1.1 才補做，導致全部參考檔重寫；跨檔的換算取整不一致，也只有跨檔比對才查得出。
  4. Skill 的成果屬工程輔助，第三級的設計與安全決策須經人工專業審查並依法簽章。

# book-to-skill：技術手冊蒸餾為 Skill

把書的「解釋順序」改寫為任務的「執行順序」。留下能讓 AI 判斷與計算的內容，刪除只為幫助理解的內容，再依任務重新排列。

## 開始前必問（缺一不可，一次問完）

1. 書名、版次、作者；使用者是否合法持有原書
2. 使用地（國家、主管機關）與契約常引用的規範
3. 目標平台（Claude／Gemini／ChatGPT，可複選）
4. 本次範圍：全書，或指定章節

未取得回答前，不讀全書、不做摘要。

## 作業流程（每步完成條件未過，不進下一步）

| 步驟 | 動作 | 產出檔 | 完成條件 |
|---|---|---|---|
| 一 定任務 | 列「動詞＋對象＋條件」任務（10～20 件為參考值），標計算／撰寫／審查／查詢；對應章節；書中沒有的列外部補充 | `tasks.md` | 涵蓋常做的工作類型且列不出新任務；每件對到章節或外部補充 |
| 二 拆 | 三遍讀法；以單元五問判斷知識單元；例題記輸入與答案 | `units.csv` | 相關章節拆完；例題全登錄；每單元有出處 |
| 三 分、濃 | 依分流矩陣決定類型、去留、改寫形式、去處 | `units.csv`（補欄） | 每單元有去處或刪除理由；受管轄者已標待本地化 |
| 四 接 | 任務追蹤五問；每步填缺漏時詢問與使用地依據（含層級與版本）；依程式化原則決定程式 | `flows/<任務>.md`、`basis.md` | 每件任務有流程表；每步有缺漏處理與依據 |
| 五 封裝 | 依放置判斷建立 SKILL.md 與參考檔；內容語意不變，依平台調整寫法與執行方式 | 目標 Skill 資料夾 | 主檔只含觸發、流程、核心決策表、索引、缺漏、常見錯誤；本文 ≤ 500 行 |
| 六 驗 | T1 數值、T2 邏輯、T3 邊界、T4 缺漏、T5 法規、T6 工程情境 | `verify.md`、`errata.csv` | T1～T5 合格，T6 已完成或已註明未做；不合格依回頭對照表修正 |

每步結束時，執行 `python3 scripts/check_units.py units.csv --step N` 檢查登錄表，並把結果與產出檔一併交給使用者確認。

## 單元五問（判斷一段文字是否為知識單元）

1. 讓讀者能做什麼（判斷、計算、選擇、檢查）
2. 在什麼條件下適用
3. 需要什麼輸入
4. 結果用在哪裡
5. 有哪些限制、例外、風險與禁止事項

五問是主要判斷工具。五題都答不出者為背景或連接敘述，不列為單元；只答得出第 5 問的安全原則或禁止事項，仍列為單元。

## 核心規則

- 公式一定連同單位、適用條件、夾限、式號一起拆出。
- 改寫時三樣不改：術語原名；式號、表號、條號；數值與單位。
- 多變數、重複、查表、複合或高精度的計算寫成程式；簡單代入依風險與平台能力決定，可逐式列出。程式須有輸入、單位與適用條件檢核，結果以例題、規範算例或獨立手算交叉驗證。
- 使用地法規、條號、版本一律查官方原文，記錄發布或修正日期、生效日期與查證日期；查不到者列入待核，不得憑記憶補寫。
- 依據分四層記錄：法令強制要求、契約與工程規範、設計方法與技術指南、補充資料。
- 單位換算保留原始值、精確值與顯示值；程式以完整精度判斷臨界條件。
- 背景與推導不放主檔；說明適用原因或例外條件者留在參考檔。
- 原書數值與使用地規定不同時，流程採使用地規定，原書值保留為參考並加註。
- 缺資料時列出缺漏並詢問，不以預設值補齊。
- 發現書的錯誤只列勘誤（位置、印刷值、正確值、判斷依據），不改原文。
- 原書內容只以摘述呈現，不大段引用；持有原書不等於取得重製或上傳授權，原表頁使用前確認授權，對外分享時排除。

## 缺漏處理

| 缺什麼 | 怎麼做 |
|---|---|
| 書的內容（只有書名） | 請使用者上傳目錄與相關章節；不憑記憶重建書的內容 |
| 使用地依據 | 詢問國家、主管機關、契約規範；仍不明則全部列待核 |
| 例題答案 | 標示「無驗證基準」，改以規範算例或獨立手算驗證，並告知驗證強度較低 |
| 平台限制 | 查該平台現行說明；查不到時依 packaging.md 的保守做法 |

## 常見錯誤

- 沒有任務清單就開始讀，結果變成全書摘要。
- 依章節順序寫主檔，主檔像目錄。
- 只抄公式、不抄適用條件。
- 失敗案例只寫成故事，沒有轉成審查檢核項。
- 本地化事後才補，參考檔全部重寫。
- 以取整後的顯示值判斷臨界條件。
- 發現書籍錯誤就直接改，失去出處可追溯性。

## 交付

最後交給使用者：目標 Skill 資料夾（或各平台版本）、`units.csv`、`flows/`、`basis.md`（含待核清單）、`verify.md`、`errata.csv`，並列出仍待使用者查核的法規版本與待核項目。Skill 產出屬工程輔助成果，不取代法定設計責任；設計與安全決策須經人工專業審查，並依法令由專任工程人員或執業技師簽章。

主檔開頭的 YAML 欄位已以解析器驗證可正確讀取，欄位內沒有全形空白或定位字元；複製全文建立 SKILL.md 時，--- 與欄位名稱須從行首開始。check_units.py 以表A1 的範例列測試，檢查至步驟三全數通過，檢查至步驟六時正確指出缺驗證項目的例題列。本 Skill 尚未以整本書實際走完六步驟，宜先選一章試做。

使用方式

  1. 將 book-to-skill 資料夾壓縮為 ZIP，上傳至平台的 Skill 設定頁；Claude Code 則將資料夾放在 .claude/skills/ 目錄下。
  2. 開新對話，上傳原書目錄與要處理的章節，輸入「把《書名》第 3 章做成 Skill」。
  3. 回答 Skill 提出的四個開始前問題，包括書名版次、使用地依據、目標平台與處理範圍。
  4. 每步結束時檢查 Skill 交出的產出檔與 check_units.py 結果，確認後再回覆進入下一步。
  5. 步驟六中 T1～T5 測試合格後，取得目標 Skill 資料夾、依據檔案與勘誤表，並自行查核待核清單中的法規版本。
